# EPUB Continuous Scroll Navigator (Reflowable)

This document describes the implementation strategy for a new, dedicated continuous vertical scrolling navigator for reflowable EPUB publications.

## Goals

- Provide a true continuous vertical scrolling experience across the full publication.
- Preserve locator fidelity and reading progression accuracy:
  - Bookmarks
  - Highlights / decorations
  - Resume / last-known position
- Support navigation to any `Locator` reliably (TOC, search results, bookmarks).
- Reuse as much existing per-resource Readium JavaScript logic as possible.
- Avoid maintaining two separate JS “feature stacks” for reflowable behavior.
- Keep the existing paginated EPUB navigator intact.

## Non-goals

- Fixed-layout (FXL) EPUB support in continuous scroll.

## High-level approach

Create a new navigator alongside `EPUBNavigatorViewController`, tentatively named:

- `EPUBContinuousNavigatorViewController`

This navigator uses **a single `WKWebView`** that loads a wrapper HTML document. The wrapper is responsible for rendering the book as a vertically scrollable document by embedding spine items as **iframes**.

### Why iframes

- Each spine resource retains its own document URL and base URL semantics.
- Existing HTTP serving and transformation pipeline can be reused.
- Existing per-resource JS can run inside each iframe with fewer URL rewriting concerns than inline injection.

## Wrapper document

The wrapper is served from the existing `HTTPServer` (same mechanism used by the EPUB navigators).

Responsibilities:

- Provide the scroll container (the wrapper document is the scroll container).
- Insert one iframe per loaded spine resource.
- Insert a separator element between chapters.
- Provide orchestration logic (mount/unmount/prefetch, routing commands to a specific iframe, computing global location).

## Key invariants

- All spine resources are served through the same `HTTPServer` origin so the wrapper can access `iframe.contentWindow` and `iframe.contentDocument` directly.
- Iframes must be sized so that chapters do not scroll internally.
- Content stability is a first-class requirement: mounting/unmounting resources and late layout changes (fonts/images) must not cause visible jumps.

### Chapter separators

Separators are generated by Swift and injected as HTML.

Proposed API shape:

- A Swift closure returning HTML:
  - `(ChapterSeparatorContext) -> String`

Where `ChapterSeparatorContext` includes:

- `href`
- `spineIndex`
- `title` (best-effort)

The returned HTML is inserted as-is into the wrapper DOM between two consecutive spine items.

## JavaScript strategy

### Key principle

Reuse the existing per-resource JS logic inside the iframe documents.

- The iframe documents run the same scripts they run today for reflowable resources.
- The wrapper adds a small orchestrator layer to:
  - know which iframe is visible
  - route “go to locator” and “apply decorations” to the right iframe
  - aggregate “current location” from the visible iframe

### Wrapper orchestrator script

A new script (tentatively `readium-continuous-wrapper.js`) is loaded only by the wrapper document.

Responsibilities:

- Build and update the list of loaded iframes.
- Maintain a mapping:
  - spine index -> iframe DOM node
  - href -> spine index
- Provide functions callable from native code:
  - `goTo(locator)`
  - `findFirstVisibleLocator()`
  - `applyDecorations(group, decorations)` (routes by href)
- Listen to scroll events and/or iframe messages to detect the active resource.

### Communication model

- Native -> wrapper: `evaluateJavaScript(...)` on the single wrapper `WKWebView`.
- Wrapper -> iframe: `iframe.contentWindow.postMessage(...)` and/or direct function calls when same-origin.
- Iframe -> wrapper: `postMessage` (e.g. progression updates).
- Wrapper -> native: use existing message handler patterns to report location changes.

## Visibility detection

The wrapper must efficiently detect which iframes are visible and which iframe is considered “active”.

- Prefer `IntersectionObserver` to avoid heavy work in scroll handlers.
- Use a conservative heuristic, such as considering an iframe active when it is the top-most iframe with a sufficiently high visible ratio.

If `IntersectionObserver` is not available or behaves unexpectedly, fall back to a throttled scroll listener.

## Iframe sizing and resize propagation

The wrapper is the scroll container, therefore each chapter iframe must be resized to match its content height.

- The iframe document reports its height to the wrapper.
- The wrapper updates the iframe element height.
- Height changes that occur above the current viewport must be compensated (see Scroll anchoring).

The resize reporting must account for:

- initial load
- late-loading images
- late-loading fonts
- user preference changes that reflow content

### Height reporting mechanism

The iframe document reports height changes using `ResizeObserver`.

Font loading is detected using `document.fonts` so that the final height is reported after fonts are applied.

## Scroll anchoring

Scroll anchoring is required to prevent layout shifts when:

- a chapter iframe above the viewport changes height
- an iframe is mounted/unmounted above the viewport

The wrapper keeps the user’s visual position stable by adjusting the wrapper scroll offset based on the height deltas of elements above the viewport.

## Locator + progression pipeline

### Current location

The navigator’s “current location” is derived from:

1. Determine the most visible iframe (or the one containing the first visible reading element).
2. Ask that iframe for its first visible element locator using existing per-resource JS:
   - `readium.findFirstVisibleLocator()`
3. Convert the iframe locator into a publication-level `Locator`:
   - Preserve the resource `href`
   - Preserve fragment/locations
4. Compute a global `Locator.locations.totalProgression`.

### Global `totalProgression`

In v1, global total progression should be computed using the publication’s `positions()` service.

- Locate the returned `Locator` into a position in the publication.
- Map it into `totalProgression`.

This matches existing behavior expectations for bookmarks/search.

## Navigation

### `go(to locator:)`

- Determine the target resource by `locator.href`.
- Ensure the target iframe is loaded (prefetch if necessary).
- Route a `readium.scrollToLocator(locator)` call into that iframe.
- Scroll the wrapper to bring the iframe into view if needed.

### Directional navigation

In continuous mode, `goForward` / `goBackward` should scroll the wrapper vertically by a configured amount.

- No horizontal pagination.
- The continuous navigator should still conform to the same public navigator protocols, but the semantics of “forward/backward” become vertical.

## Decorations (highlights, annotations)

Decorations remain Locator-based.

Proposed routing:

- Group decorations by `href`.
- For each `href`:
  - ensure iframe is loaded (or defer until it is)
  - apply decorations in that iframe using existing per-resource JS decoration API

User interaction:

- Decoration activation events from iframes are forwarded to native.

## Search

Search stays publication-level:

- The existing `SearchService` returns locators.
- In continuous mode, the app calls `go(to:)` with the result locator.
- Optional: a “search group” decoration group can be applied for the active result.

## Performance and loading strategy

Continuous scroll must be bounded in memory.

- Maintain a sliding window of mounted iframes around the current resource.
- Replace unloaded chapters with spacer elements to preserve scroll height.
- Keep an overscan region so users never land inside a spacer.

The window size must be configurable, with a conservative default (for example: 1 behind, current, 2 ahead; and a hard cap such as 7 total mounted iframes).

When mounting/unmounting and when iframe heights change, the wrapper must apply scroll anchoring to prevent visible jumps.

### Optional CSS optimizations

The wrapper may optionally evaluate CSS containment or `content-visibility` on spacer elements and/or chapter containers, provided it is supported and beneficial in WebKit.

## Decisions and rationale

This plan intentionally avoids hard-committing to a few techniques which may be beneficial but are not required for correctness.

- CSS containment / `content-visibility`
  - Kept as optional because benefits and support can vary in WebKit, and the core design should not depend on a CSS optimization which might not pay off.
- `contentvisibilityautostatechange`
  - Not included because it is too speculative for WebKit and should only be considered after validating that `content-visibility` is both supported and materially beneficial.
- Hard performance numbers (for example: 60 fps scroll, 100 ms navigation)
  - Not included as requirements in this architecture document. These are QA targets and should be derived from real measurements once a working implementation exists.

## Accessibility

The continuous navigator must define an accessibility strategy and be tested with:

- VoiceOver (including “Read All” / continuous reading across chapter boundaries)
- Switch Control
- Voice Control

Chapter boundaries must be discoverable (e.g. by labelling chapter regions using the best-effort title), without harming the reading experience.

## JavaScript error boundaries

Per-resource failures must not break the wrapper.

- If an iframe fails to load or initialize, the wrapper marks the chapter as failed and can retry.
- Errors should be reported to native using the existing logging bridge.

## Testing strategy

Testing should cover:

- Locator navigation to chapters that are not currently mounted.
- No visual jumps when:
  - mounting/unmounting chapters above the viewport
  - images/fonts load late in chapters above the viewport
- Decoration routing and interaction callbacks across mount/unmount.
- VoiceOver “Read All” continuity across chapter boundaries.

## Public API

The continuous scroll navigator is exposed as a **separate navigator type**, not a toggle on the existing one.

Expected consumer behavior:

- Choose which navigator to instantiate for a given publication.
- Continuous scroll is supported for reflowable EPUB only.

## Error handling and fallbacks

- If the publication is fixed-layout:
  - reject continuous navigator creation (or fall back to existing paginated navigator, depending on desired behavior).

## Future work: Fixed-layout (FXL)

FXL can have its own continuous navigator variant, but it should be planned as a distinct implementation due to:

- zoom/scaling semantics
- one-page vs two-page spreads
- fixed viewport constraints

A future API may expose both:

- existing paginated FXL navigator
- optional continuous FXL navigator

…but this is intentionally not part of this plan.

## Milestones

1. Wrapper + iframe rendering for reflowable reading order.
2. Visibility detection and active resource tracking.
3. Iframe sizing and resize propagation (including late images/fonts).
4. Sliding window mounting/unmounting with spacers.
5. Scroll anchoring for height changes and mounting/unmounting.
6. Basic navigation:
   - `go(to locator:)`
   - `goForward`/`goBackward` vertical scroll
7. Location reporting:
   - first visible locator
   - `totalProgression`
8. Decorations routing (grouped by href) and interaction forwarding.
9. Accessibility validation and refinements.
